# 远程接入平台设计

日期：2026-10-06

状态：设计（待评审）

范围：**平台侧** —— 中转服务、客户端渠道层、接入契约。**不含**各接入方侧的具体改造（第一个接入方另行设计）。

**项目归属**：本设计描述的是一个**独立项目**，与任何既有的桌面应用项目相互独立。文中凡引用既有实现的地方，一律只作**先例或论据**，不构成本项目的现成依赖；凡属"要不要与既有实现共享代码"的取舍，都在对应章节（§5.8）给出结论并说明理由。

## 1. 背景与定位

### 1.1 需求来源

桌面 AI 应用常驻在员工电脑上，可用的能力大多在本机执行。用户希望在**不在电脑前**的时候，也能从手机上继续使用这套能力：看进度、发消息、中断执行、审批 Agent 的请求、回答 Agent 的提问，以及让 Agent 操作那台电脑上的工作区。

提出时的原始设想是"小程序直接连业务服务端"。该设想不成立，原因见 §1.4。最终确定的形态是：**手机连一台常驻在本机的接入服务，由这台服务继续对业务服务端说话。**

### 1.2 定位：平台三要素

本设计交付的不是"给某一个桌面客户端加一个手机端"，而是一个**可复用的远程接入平台**：

1. **中转服务** —— 哑管道。为处在不同网络里的两端提供会合点，只做配对与帧转发。
2. **客户端渠道层** —— 一组可扩展的客户端渠道（纯 Web、钉钉、飞书、企业微信、微信小程序……）。渠道之间的差异被隔离在这一层。
3. **接入契约** —— 桌面 AI 应用要实现的一套稳定接口。**任何符合契约的桌面应用都可以接入**，不需要平台为它改代码。

### 1.3 与接入方的关系

接入方是**平台的用户**，不是平台的一部分。

- 平台不承载接入方自己的会话模型、机器标识、工作区这类业务概念。
- 每个接入方需要新增一个常驻的接入服务，把它自己的"会话"映射成契约里的 `Conversation`，把它的消息单元映射成 `Message.Block`。这件事**不在本设计范围内**，本设计只规定它必须满足什么。
- 本设计的验收方式之一，就是任何一个接入方能否在**不修改平台**的前提下完成接入。

### 1.4 为什么是这个形状（曾经考虑过并否决的替代）

**替代一：客户端直连业务服务端，手机也直连业务服务端。** 否决。三条现有约束各自独立地否掉了它：

- 会话与工作区按物理机隔离：建立会话必须携带机器标识，查询本机工作目录也必须带同一标识，且同一用户在不同机器上只看到各自机器创建的会话。手机是另一台物理机，天然看不到电脑上的会话。
- 同一个会话在同一时刻只能被一条连接操作：第二条连接尝试驱动它会被直接拒绝。手机与电脑不能同时驱动同一个会话。
- Agent 的文件与 Shell 工具**不在服务端执行**，而是委托给持有连接的那个客户端。手机没有电脑的文件系统和 Shell，一旦由它持有连接，Agent 的核心能力就断了。

**替代二：局域网直连。** 部分可行但不满足需求。微信小程序确实支持与同网段非本机 IP 通信且免域名校验（官方文档《网络 · 使用说明》《局域网通信》），但用户明确需要**外网（4G／外地）也能遥控**。外网场景下手机与电脑同时处在各自的 NAT 之后，且小程序没有任何 P2P 打洞能力（没有 `createRTCPeerConnection` 一类 API），**必须有一个双方都能连到的会合点**。这是网络拓扑的必然结果，不是技术选型问题。

**替代三：平台统一账号体系。** 否决。平台的卖点是"任何桌面 AI 应用都能接入"。如果平台自带账号，每个接入方都要把自己的用户体系接进平台，接入门槛被显著抬高；平台也会因此从哑管道变成持有用户数据的服务。详见 §8.1。

**替代四：声明式 UI（接入方下发界面描述，客户端通用渲染）。** 否决。既有的插件化桌面应用确实常走声明式 UI（可作先例），那套做法成立是因为**外部扩展的代码不可信、不能进应用的 React 运行时**。远程接入的处境完全不同：**接入方的代码和界面根本不会跑在客户端渠道里**，每个渠道有自己固定的界面。此时声明式 UI 只会把移动端 UI 适配成本推给每一个接入方，与"降低接入门槛"的目标相反。结论：**接入方给数据和动作，平台给界面。**

## 2. 目标与非目标

### 2.1 目标

- 让桌面 AI 应用的使用者在**任意网络位置**（含 4G／异地）通过平台提供的客户端渠道操作自己的电脑。
- 覆盖的操作为：查看会话列表、查看与接收消息流、发送消息、中断执行、响应审批／提问、查看执行进度、浏览本机工作区文件。
- 平台对**多个接入方**开放，接入契约稳定、可版本协商。
- 平台对**多个客户端渠道**开放，新增渠道时接入方零改动。
- 平台保持哑管道定位：不解析业务载荷、不持接入方 token、不落业务数据。

### 2.2 非目标

- **各接入方侧的具体改造**（会话所有权下沉、常驻服务实现、进程模型等）—— 由接入方自行设计。
- 声明式 UI。
- 平台统一账号体系。
- 局域网直连快路径。
- 应用市场与安装期能力同意。
- 移动端的代码高亮、Diff 预览、原文件预览、扩展页面、工作区切换。
- 平台侧"一键撤销已发放的会话密钥"—— 物理上做不到，见 §8.5。

## 3. 术语

| 术语 | 含义 |
|---|---|
| **平台** | 中转服务 + 客户端渠道层的总和 |
| **接入方 / Endpoint** | 一个桌面 AI 应用在本机的常驻服务实例 |
| **客户端渠道 / Channel** | 用户侧的载体：纯 Web、钉钉、飞书、企业微信、微信小程序…… |
| **中转** | 平台内负责配对与转发的服务 |
| **会话 / Conversation** | 契约核心模型中的一次对话 |
| **交互 / Interaction** | 契约核心模型中的"需要用户回答的请求"：审批、提问、高危确认 |
| **配对 / Pairing** | 把一个客户端实例与一个 Endpoint 建立长期授权关系的过程 |
| **断言 / Assertion** | 客户端交给接入方自行校验的身份凭证（如 JWT）。平台只转发，不解析 |

## 4. 总体架构

### 4.1 四要素

```
┌ 客户端渠道 ─┐        ┌─ 平台 ────────────────────┐        ┌─ 接入方（员工电脑）─┐
│ 纯 Web      │        │  渠道适配层  中转（哑管道） │        │  常驻接入服务       │
│ 钉钉/飞书   │─wss──▶ │      │          ▲          │ ◀─出站wss─│  （桌面客户端）    │──▶ 业务服务端
│ 企业微信    │        │      └──────────┘          │        │                     │
│ 微信小程序  │        └───────────────────────────┘        └─────────────────────┘
└────────────┘
```

接入方**主动出站**连接中转（所以与 NAT 无关）；客户端渠道也连接中转；中转按配对关系把两者关联并双向转发。

### 4.2 职责边界

| 角色 | 负责 | **不负责** |
|---|---|---|
| 中转 | 设备上线注册、配对路由、帧转发、连接元数据审计 | 解析业务载荷、持接入方 token、存业务与用户数据、理解"会话"的业务含义 |
| 渠道适配层 | 传输方式、身份断言获取、渲染载体、触达 | 理解业务语义、替接入方做身份裁决 |
| 渠道客户端 | 固定界面、配对、按能力裁剪、断连恢复 | 运行接入方代码、执行业务逻辑 |
| 接入方 | 身份校验、会话与执行、事件发布、高危确认的发起 | 定义协议、定义客户端界面 |

三句话概括：

1. 平台不知道"会话"的业务含义，只负责把它送到客户端上、把回答带回来。
2. **接入方的界面不进客户端** —— 每个渠道只有平台自己的固定界面。
3. **身份是接入方的事**，平台只保证通道的真实性与保密性。

### 4.3 渠道无关性不变量（本设计的核心不变量）

> **接入契约必须渠道无关。任何为某个渠道新增的字段、能力或语义都是设计缺陷。**

理由：渠道会持续增加（微信小程序 → 钉钉 → 飞书 → 企业微信 → …）。如果每个新渠道都要求接入方改代码，平台就失去了存在意义。

**验收方式（硬性）**：新增一个渠道时，接入方**零改动**；该渠道只新增一个适配器实现与一套渠道界面。

**落地手段**：渠道特有的限制（如"进后台 5 秒网络请求被中断""主包体积上限"）由**渠道自己声明**，平台与接入方据此裁剪行为，而不是把限制写进契约。

## 5. 接入契约

### 5.1 接入方的形态要求

接入方必须提供一个**常驻服务**，它能够：

- 主动出站连接中转，并维持长连接；
- 管理本 Endpoint 的密钥对与已授权客户端清单；
- 处理 §5.3 的指令，发布 §5.4 的事件；
- 完成配对校验（校验方式由接入方自己决定，见 §8.3）；
- 声明自己的能力集。

契约**不规定实现**：语言、进程模型、是否嵌在 GUI 应用里、如何持久化，全部由接入方决定。平台不检查接入方的实现，只检查它与契约的交互。

### 5.2 固定核心模型

契约定义一套所有桌面 AI 应用都具备的最小模型。接入方把自己的概念映射到这套模型上。

| 模型 | 最小字段 | 说明 |
|---|---|---|
| `Endpoint` | `appId`、`deviceId`、`displayName`、`capabilities[]`、`contractVersion` | 一个接入应用实例 |
| `Conversation` | `id`、`title`、`updatedAt`、`active` | `active` 为真表示正在执行，决定"能否中断" |
| `Message` | `id`、`role`（`user`／`assistant`／`system`）、`createdAt`、`blocks[]` | 一条消息 |
| `Interaction` | `id`、`kind`（`approval`／`input`／`confirm`）、`title`、`detail?`、`responseSchema`、`status`（`pending`／`answered`／`expired`）、`createdAt` | 需要用户回答的请求 |

`Block` 是多态的，以 `type` 判别：

| `type` | 载荷 | 说明 |
|---|---|---|
| `text` | `text` | 支持流式增量 |
| `reasoning` | `text` | 思考过程，客户端默认折叠 |
| `tool` | `name`、`status`（`running`／`succeeded`／`failed`）、`summary`、`detail?` | `detail` 是受限的声明式节点子集，见 §5.8 |
| `file` | `name`、`size?`、`mime?` | 文件卡片，不预览 |
| `image` | `artifactId`、`mime?` | 经中转拉取缩略图，见 §7.3 |
| `notice` | `level`（`info`／`warning`／`error`）、`text` | 错误与系统提示 |
| `unknown` | `raw` | **未知类型必须能落地到这里**，不能崩、不能空白 |

`unknown` 是强制项，不是可选项：没有它，接入方升级契约后老客户端会直接白屏。

### 5.3 指令（客户端 → 接入方）

**核心必备**（所有接入方必须实现）：

| 指令 | 作用 |
|---|---|
| `endpoint.describe` | 返回显示名、能力集、契约版本 |
| `conversation.list` | 列出会话 |
| `conversation.subscribe` / `conversation.unsubscribe` | 订阅／取消订阅某会话的事件流 |
| `message.send` | 向会话发送消息（含块数组） |
| `conversation.interrupt` | 中断当前执行 |
| `interaction.respond` | 回答交互请求 |

**可选**（由能力开关控制，见 §5.5）：

| 指令 | 对应能力 |
|---|---|
| `conversation.create` | `conversation.create` |
| `file.pick` | `file.pick` |
| `attachment.upload` | `attachment.upload` |
| `artifact.fetch` | `artifact.fetch` |

接入方收到未声明能力对应的指令时，必须返回明确错误（形状判定，不使用 `instanceof`），不得静默忽略。

### 5.4 事件集与序号

接入方向客户端推送：

`endpoint.updated`、`conversation.updated`、`message.appended`、`block.delta`、`block.updated`、`interaction.requested`、`interaction.updated`、`conversation.active.changed`。

**每条事件必须带单调递增序号 `seq`**。这是断连恢复的唯一基础：客户端重连后按 `lastSeq` 请求补发；接入方无法补发时返回一份当前快照，客户端整体替换。

`seq` 是**每个 Endpoint 一条序列**，不是每个会话一条 —— 否则客户端要为每个会话维护独立的恢复点。

### 5.5 能力开关

接入方在 `endpoint.describe` 中返回 `capabilities[]`。平台把它透传给客户端，**客户端据此裁剪界面**：没有 `conversation.create` 就不显示"新建"；没有 `file.pick` 就不显示"@文件"。

约束（沿用既有实现已经验证过的做法，关于"先例与本项目资产"的区分见 §5.8）：

- **方法到能力的绑定只有一处**，是单一事实来源；
- **查表一律防原型**（`Map`／`Object.hasOwn`／`Object.create(null)`）—— 能力 id 来自外部输入，普通对象字面量会让 `toString`、`constructor` 这类键查到 `Object.prototype`；
- 客户端**不得**因为遇到未知能力而失败，只忽略。

### 5.6 交互与高危确认

`Interaction` 有三种 `kind`，客户端用同一个组件按 `kind` 渲染：

| `kind` | 来源 | 语义 |
|---|---|---|
| `approval` | 接入方的业务审批协议 | 批准／拒绝 |
| `input` | 接入方需要用户补充信息 | 自由回答 |
| `confirm` | 接入方在执行**有副作用的操作**前发起 | 确认／取消 |

**高危确认不新增协议机制** —— 它就是 `Interaction` 的一种 `kind`。

**接入方义务**：执行有副作用的操作（如在本机运行命令、写入或删除文件）之前，必须先发一个 `kind = 'confirm'` 的交互并获得肯定回答。

**⚠️ 诚实边界（必须写进契约文档，不能省略）**：平台**无法强制**接入方履行这条义务 —— 接入方是它自己控制的进程，平台看不到它内部做了什么。平台能提供的只有两件事：

1. 在 `endpoint.describe` 时记录接入方声明的能力；
2. 把**所有**交互请求与回答写入审计（§9.3）。

因此这条义务的正确表述是：**平台只能见证，不能保证。** 如果有人以为平台兜住了高危操作，就会在安全评估时得出错误结论。

### 5.7 版本协商与容错

- **契约版本是单一事实来源**，只在契约层定义一处。
- `endpoint.describe` 时协商版本：接入方声明 `contractVersion`，平台与客户端按协商结果决定可用字段；协商不出交集时明确拒绝，不猜测。
- **未知块类型 → `unknown` 兜底渲染**；**未知枚举取值 → 归一为默认值，不判为错误**。理由：如果把"新增枚举取值"判为错误，一个 minor 变更就变成了破坏性变更。既有实现对未知取值一律归一的理由与此完全一致（见 §5.8）。
- **未知指令 → 明确错误**，用形状判定而非 `instanceof`（跨模块实例会静默失效）。
- **`undefined` 不是合法 JSON 值**：字段缺失要**省略键**，不要写 `undefined`。
- 内容块设**字节与深度上限**：可直接沿用既有实现已验证过的那组预算（单次载荷 256 KiB、节点数 2000、深度 32），不需要重新调参。深度上限是必需的，不是保守 —— 深层嵌套的合法 JSON 会在远低于字节预算时触发 `RangeError`。

### 5.8 内容块的表达方式，以及一个必须避开的坑

**做法**：`tool` 块的 `detail` 用**受限的声明式节点子集**表达。不同接入方的工具有不同形状，这里确实需要一点通用性。

**先例（不是本项目的现成依赖）**：既有的插件化桌面应用实现过一套同类模型 —— 声明式节点类型、结构校验、度量与限额，纯 TypeScript、无 DOM 依赖。本项目有两条路：**依赖那套既有实现，或借鉴其形状重写一套**。

**结论：重写。** 理由是把契约的单一事实来源留在本项目内 —— 依赖外部实现会把两个项目的发布节奏绑在一起，而两者的演进目标并不相同（那套模型是为"让不可信的第三方扩展渲染任意界面"设计的，本项目是为"受限的工具详情展示"设计的）。

**坑（必须写进契约）**：那套既有实现的界面度量部分依赖 `TextEncoder`，而**微信小程序运行时没有 `TextEncoder`**。沿用会直接踩到。因此：

> **内容块的校验必须在接入方与平台侧完成，客户端渠道只做渲染降级。**

不说清楚，接入方会以为客户端会兜住校验。按这个分工，渠道侧本来就不需要度量函数 —— 重写时也就不必把 `TextEncoder` 依赖带进来。

## 6. 中转服务

### 6.1 职责（穷举）

中转**只做**以下六件事：

1. 接受接入方的出站长连接注册；
2. 接受客户端渠道的连接；
3. 按配对关系关联两条连接并双向转发帧；
4. 维护在线状态，并把状态变化通知对端；
5. 断线时通知对端；
6. 记录连接元数据供审计。

超出这个清单的需求，默认属于接入方或渠道层。

### 6.2 两条接入路径与鉴权

| 谁 | 连接 | 鉴权 |
|---|---|---|
| 接入方 | `wss://<relay>/agent` | 平台签发的注册凭据（`appId` + 密钥） |
| 客户端渠道 | `wss://<relay>/remote` | 首次用短时效、单次有效的 `pairToken`；之后用会话密钥签名 |

### 6.3 帧信封与明文控制帧

业务帧统一封装为信封：

```
{ channel, seq, nonce, ciphertext, tag }
```

**中转只看到信封**。此外中转必须理解一组**明文控制帧**，否则无法完成配对与转发：`register`、`pair`、`pair.ack`、`ping`、`offline`、`bye`。

控制帧只含路由与状态信息，**不得包含业务内容**。

### 6.4 连接粒度与上限

**一条连接对应一个 Endpoint。** 配对粒度就是 Endpoint，所以这是最自然的模型。

已知限制：微信小程序的 `wx.connectSocket` 并发上限为 5，因此该渠道**同时最多 5 个 Endpoint 在线**。一期渠道是纯 Web，不受此限制；接入微信小程序渠道时需在渠道限制声明中体现。

### 6.5 背压与重同步

事件流以高频增量（`block.delta`）为主，慢客户端会让转发缓冲无限增长。因此：

- 中转按客户端消费能力**允许丢弃**事件；
- 丢弃是**正常路径**，客户端用 `seq` 重新同步（请求补发或拉快照）。

不做背压的中转在首个弱网客户端上就会内存失控。

### 6.6 在线状态与断线

- 同一 `deviceId` 只允许存在**一个活跃注册**；重复注册按幂等重连处理，旧连接被替换。
- 接入方断线必须通知已配对的客户端，客户端据此显示"电脑离线"并转入重试。
- 客户端断线不要求接入方停止执行 —— 执行属于业务，不属于通道。

### 6.7 部署约束

中转是所有接入方与所有渠道的**共同依赖**：它不可用时，全部远程访问同时失效。因此部署上需要考虑多实例与连接状态外置。本设计不规定具体部署形态，但要求这一点在设计评审时被显式确认，不能默认单实例。

## 7. 客户端渠道层

### 7.1 渠道族

渠道不是一个平面列表，而是一个**族**：

```
渠道族
├── 纯 Web（浏览器）        ← 一期
├── IM 容器 H5 族           ← 共用同一套 Web UI 与传输实现
│   ├── 钉钉
│   ├── 飞书
│   └── 企业微信
└── 微信小程序              ← 独立技术栈，需要单独实现界面与传输
```

IM 容器 H5 族之间真正的差异只有两点：**身份断言怎么获取**（各家免登 JSAPI）与**触达怎么发**（工作通知／消息卡片／应用消息）。传输与界面是共用的。

### 7.2 渠道适配器契约

每个渠道实现一个适配器，声明以下关注点：

| 关注点 | 说明 |
|---|---|
| `channelId` | `web`／`dingtalk`／`feishu`／`wecom`／`wechat-miniprogram` |
| 传输 | 该渠道可用的长连接方式（标准 `WebSocket`／`wx.connectSocket`／降级为 SSE） |
| 身份断言 | 该渠道能提供什么断言（门户 OAuth 令牌／钉钉免登 code／微信 openid…）。**平台不裁决，只当断言转给接入方** |
| 渲染载体 | H5／小程序组件 |
| 触达 | Web Push／工作通知／消息卡片／订阅消息 |
| **限制声明** | 渠道自己声明能力与限制（后台断连、体积上限、并发上限），平台与接入方据此裁剪 |

最后一行是 §4.3 渠道无关性不变量的落地手段。

### 7.3 一期渠道：纯 Web

**一期只做纯 Web，不接任何 IM 平台。** 理由：

- 不需要任何 IM 平台的应用注册、主体审核与域名配置 —— 平台本身可以先跑起来；
- 浏览器有**标准 `WebSocket`** 与 **WebCrypto**，绕开了小程序渠道下两个最大的不确定性（见 §11）；
- 一套 Web UI 之后可同时覆盖钉钉／飞书／企业微信三个渠道；
- 没有小程序的主包体积限制，Markdown 渲染不需要分包。

**身份断言**：一期用已有的门户 OAuth（HTTPS 回调，浏览器天然支持）。这也是接入方 `assertion` 模式的第一个真实用例。

**已知限制（渠道限制声明的第一批内容）**

- 移动端 WebView 在应用切后台后会被挂起，长连接随即断开。**这是移动端通病，H5 与小程序一样存在**，不是某个渠道的缺陷。恢复策略见 §10.5。
- **图片与产物必须经中转**：客户端不直连业务服务端，而资源访问需要接入方的凭据。因此一期策略是"**缩略图经中转，原文件不预览**"，并在渠道限制中声明。

### 7.4 渠道演进路径

1. **纯 Web**（一期）；
2. **IM 容器 H5**（钉钉／飞书／企业微信）：新增免登断言适配器与触达适配器，复用同一套 Web UI 与传输实现；
3. **微信小程序**：需要独立实现 WXML/WXSS 界面、`wx.connectSocket` 传输适配器，并显式处理其特有约束（后台 5 秒断连、主包 2MB、并发 5、无 `TextEncoder`）。

### 7.5 渠道无关性的验证方式

每新增一个渠道，必须验证：

- 接入方**零改动**（代码与配置都不变）；
- 该渠道的特有限制**只出现在渠道适配器与渠道限制声明中**，没有渗进契约。

## 8. 配对与身份

### 8.1 三层分工

平台中立的具体落地方式是把"身份"拆成三层，各自归属不同：

| 层 | 归属 | 内容 | 防什么 |
|---|---|---|---|
| 通道鉴权 | **平台** | 接入方注册凭据；客户端首次配对的 `pairToken` 单次、短时效 | 未授权连接、配对码猜解 |
| 端到端会话密钥 | **两端**（平台只搬运公钥） | 两端各自生成密钥对，经平台交换公钥，ECDH 派生会话密钥 | 平台被攻破、内部人、网络窃听 |
| 人员身份 | **接入方** | 接入方声明校验方式并自行裁决；平台只转发断言与结果 | 别人用自己的设备控制你的电脑 |

**为什么人员身份不归平台**：平台要支持多个桌面 AI 应用，这些应用各有各的账号体系。平台自带账号会迫使每个接入方对接平台的用户体系，显著抬高接入门槛；同时平台会从哑管道变成持有用户数据的服务，安全边界随之扩大。

### 8.2 配对流程

1. 接入方在本机生成**短时效配对码**，内容为 `appId`、`deviceId`、一次性 `pairToken` 与有效期，以二维码形式展示。
2. 客户端扫描 → 连接中转 → 发送 `pair{ appId, deviceId, pairToken, clientPublicKey }`。
3. 中转校验 `pairToken`（单次、有效期内）后路由给对应接入方。
4. 接入方执行**双向确认**：在本机界面上询问"是否允许这台设备接入"。同时按其身份校验方式校验断言（§8.3）。
5. 接入方回传 `agentPublicKey` 与校验结果；两端各自 ECDH 派生会话密钥。
6. 双方持久化配对记录：接入方保存 `{ deviceId, clientPublicKey, 授权范围, 授予时间 }`；客户端保存 `{ appId, deviceId, agentPublicKey }`。
7. 此后每次连接直接用会话密钥完成握手，不再需要配对码。

**为什么必须有第 4 步的双向确认**：配对码显示在电脑屏幕上，能扫到它的人已经具备了某种程度的物理接触。但"看到屏幕"与"就是这台电脑的使用者"不是一回事（未锁屏、临时离开）。双向确认把这一跳补齐，成本极低。

### 8.3 身份断言扩展点

契约里定义：

```
identity: { mode: 'none' | 'assertion', schema?: object }
```

- **`none`**：只依赖物理接触与 §8.2 的双向确认。适用于敏感度低的场景。
- **`assertion`**：客户端必须出示一个**接入方认识的断言**。平台**原样转发、不解析、不存储**，由**接入方自行验签**。`schema` 描述接入方期望的断言形状。

第一个接入方将以 `assertion` 模式接入：客户端出示企业门户签发的 JWT，接入方使用自己已有的 OIDC 能力验签，并要求断言中的用户标识必须等于本机已登录的用户标识。**这是接入方的实现，不是平台的规定** —— 平台只知道"有一个断言被转发了"。

### 8.4 多客户端与写指令串行化

配对模型是**一个 Endpoint 对多个客户端**（同一用户的多台设备、换机、备用机）。多客户端同时在线时，事件**多播给所有已授权客户端**。

但写指令（`message.send`、`interaction.respond`、`conversation.interrupt`）必须串行化：

- 平台只按到达顺序转发，**不判断**"当前是否已有执行中的请求"（那是业务语义）；
- **串行化是接入方的责任**：接入方必须串行化写指令并返回明确错误（例如"已有执行进行中"），不得让两个客户端的请求互相覆盖。

这条要写进契约，否则平台会被误以为做了并发控制。

### 8.5 吊销与其物理限制

| 层次 | 能做什么 | 限制 |
|---|---|---|
| 接入方 | 设备清单、一键吊销、拒绝握手 | 这是**唯一真正有效**的撤销点 |
| 平台 | 解除 `deviceId ↔ 客户端` 的配对关系 | **无法撤销已经发放到客户端的会话密钥** |

**⚠️ 诚实边界**：会话密钥在两端，平台没有它。平台侧解绑只能阻止新的握手、缩小暴露面，**不能把一个已经拿到密钥的客户端踢下线**。安全评估文档里必须写明这一点，否则会出现"平台能一键踢人"的错误预期。

配套要求（因为这条限制）：会话密钥必须有**较短的有效期**，到期后需要重新握手，而重新握手必须让接入方**重新执行身份校验**。这是把"撤销"从"平台做不到"转移为"接入方定期复查"的唯一手段。

## 9. 安全模型

### 9.1 威胁与对策

| 威胁 | 对策 | 责任方 |
|---|---|---|
| 网络窃听 | WSS（TLS 1.2+）+ 端到端加密 | 平台 + 两端 |
| 平台被攻破或内部人 | 端到端加密：平台只见密文 | 两端 |
| 凭据被复制到其他设备 | 设备非对称密钥，私钥不出端 | 两端 |
| 帧重放 | 每帧带 `seq` 与 `nonce`，接收端滑窗拒绝重复 | 两端 |
| 指令伪造 | 帧整体 AEAD 保护（或逐条签名） | 两端 |
| 客户端设备丢失 | 会话密钥短有效期 + 到期重新校验身份 + 接入方吊销 | 两端 |
| 有人短暂接触未锁屏电脑即配对 | 短时效配对码 + 接入方侧双向确认 | 接入方 |
| 别人用自己的设备控制你的电脑 | 接入方的身份断言校验（§8.3） | 接入方 |
| 慢客户端拖垮中转 | 背压丢弃 + `seq` 重同步 | 平台 |
| 高危操作无感执行 | `Interaction{ kind: 'confirm' }` | 接入方发起，**平台见证并审计** |

### 9.2 密钥与生命周期

- 每个客户端实例与每个 Endpoint 各持一对非对称密钥，私钥**不出端**。
- 配对时交换公钥并 ECDH 派生会话密钥；会话密钥**短有效期**，到期重新握手。
- 重新握手必须触发接入方重新执行身份校验（§8.4 与 §8.5 的共同要求）。
- **已知弱点**：Web 与小程序运行时的本地存储都不是硬件保护的，在已越狱／已 root 的设备上私钥可能被复制。因此"短有效期 + 可吊销"是**必需项而非增强项**。

### 9.3 审计分工

为保持"平台不落业务数据"，审计拆成两层：

| 层 | 记录 | 不记录 |
|---|---|---|
| 平台 | 连接元数据（身份标识、时间、来源 IP、时长、字节数）、**交互的发生与结果**（`interactionId`、时间戳、结果） | 业务内容、消息正文、断言内容 |
| 接入方 | 完整业务审计：谁、何时、对哪个会话做了什么、结果如何、高危确认的内容与结论 | — |

平台记录"交互的发生与结果"是为了让高危确认在平台侧有不可否认的痕迹 —— 这是平台在 §5.6 里唯一能提供的保障。

### 9.4 降级方案（显式记录，不得默认启用）

如果某个渠道无法提供所需的密码学能力（见 §11 风险一），该渠道退化为：

- 依赖 WSS 的 TLS 保护传输，**不端到端加密**；
- 保留逐帧签名与防重放；
- 平台因此**能看到明文**。

降级必须**显式配置并在渠道限制声明中标注**，不得静默发生。在端到端加密可用的渠道（如纯 Web，具备 WebCrypto）上，不得启用降级。

## 10. 典型数据流

### 10.1 配对

```
接入方 ── 生成 pairToken（短时效、单次）──▶ 本机显示二维码
客户端 ── 扫码 ──▶ 中转 ── pair{appId, deviceId, pairToken, clientPub} ──▶ 接入方
接入方 ── 本机双向确认 + 校验断言 ──▶ 回传 agentPub
两端 ── ECDH 派生会话密钥 ── 各自持久化配对记录
```

### 10.2 建立连接与订阅

```
接入方 ── 出站注册（appId + deviceId + 注册凭据）──▶ 中转
客户端 ── 连接（会话密钥握手）──▶ 中转 ──▶ 接入方
客户端 ── conversation.list ──▶ 接入方 ── 列表 ──▶ 客户端
客户端 ── conversation.subscribe{cid, lastSeq} ──▶ 接入方
接入方 ── 补发 seq > lastSeq 的事件，或回一份快照 ──▶ 客户端
```

### 10.3 发送消息与流式返回

```
客户端 ── message.send{cid, blocks} ──▶ 接入方
接入方 ── conversation.active.changed{active:true} ──▶ 全部已授权客户端
接入方 ── message.appended（assistant 消息骨架）──▶
接入方 ── block.delta × N（流式）──▶
接入方 ── conversation.active.changed{active:false} ──▶
```

### 10.4 高危操作确认

```
接入方 ── 准备执行有副作用的操作
接入方 ── interaction.requested{kind:'confirm', title, detail} ──▶ 客户端
客户端 ── 用户确认 ── interaction.respond{id, approved:true} ──▶ 接入方
接入方 ── 执行
平台 ── 记录 interaction 的发生与结果（不含内容）
```

### 10.5 断连恢复

移动端 WebView 被挂起导致的断连是常态。恢复流程：

```
客户端回到前台 ── 重连中转 ── 会话密钥握手 ──▶ 接入方
客户端 ── conversation.subscribe{cid, lastSeq} ──▶
接入方 ── 能补发则补发 seq > lastSeq；否则回快照 ──▶ 客户端
```

客户端**不得**在恢复时重放未确认的写指令 —— 这会把一次用户操作变成两次。写指令的幂等性由接入方通过请求标识保证。

## 11. 待验证风险（先行验证清单）

以下四项**必须在进入实施前完成验证**，其中第一项决定端到端加密能否落地：

| # | 风险 | 影响 | 验证方式 |
|---|---|---|---|
| 1 | **微信小程序侧没有 WebCrypto**（没有 `crypto.subtle`），ECDH/AEAD 只能靠纯 JS 库或 `WXWebAssembly` | 决定微信小程序渠道能否使用端到端加密，否则只能走 §9.4 降级 | 真机验证：在微信小程序内完成一次 ECDH + AEAD 往返 |
| 2 | 渠道长连接在切前后台时的稳定性 | 决定断连恢复策略的实际强度 | 真机验证：纯 Web 与目标渠道各测一轮 |
| 3 | 图片经中转的带宽与体验成本 | 决定一期是"缩略图"还是"完全不预览" | 用真实会话的图片负载测量 |
| 4 | 身份断言获取页的承载方式（`assertion` 模式） | 影响 IM 渠道接入的行政前置 | 纯 Web 渠道用门户 OAuth 的 HTTPS 回调，先跑通；IM 渠道接入时再确认各家免登能力 |

**注意**：一期选择纯 Web 渠道的一个直接收益是 —— 风险 1 与风险 2 在小程序侧的部分被推迟，平台可以先在具备标准 WebCrypto 的环境里跑通。**这不代表风险消失，只代表它被推到了小程序渠道接入之前。**

## 12. 测试策略

### 12.1 契约层（本项目的主力测试对象）

契约层是纯 TypeScript，纳入**本项目自己的**测试入口（命令名与形式由本项目决定，不沿用任何既有仓库的脚本）：

- 编解码与信封往返；
- 能力查表（**防原型**：`toString`、`constructor` 等键不得命中继承成员）；
- 版本协商：无交集时拒绝，交集时取最低版本；
- 未知块类型落到 `unknown`；未知枚举取值归一为默认值而非报错；
- `seq` 补发、去重、滑窗拒重；
- 字节与深度上限（含深层嵌套合法 JSON 不触发 `RangeError`）；
- 字段缺失时省略键，不产生 `undefined`。

### 12.2 中转

- 配对路由、`pairToken` 单次有效与过期；
- 幂等重连（同一 `deviceId` 重复注册替换旧连接）；
- 背压丢弃后客户端仍能通过 `seq` 恢复；
- 断线通知对端；
- 时钟与传输必须可注入 —— 这是既有实现里已经验证过有效的做法（可注入的传输工厂、可注入的请求实现），本项目沿用该模式。

### 12.3 渠道层

- 渠道限制声明被正确读取，且**不渗进契约**；
- **渠道无关性测试（硬性）**：用一个 mock 渠道（不实现任何界面，只走协议）验证接入方零改动即可工作。这是 §4.3 不变量的自动化保障。

### 12.4 契约兼容性

- **至少两个实现**（一个真实接入方 + 一个最小 mock 接入方）跑同一套契约断言。这是契约不跑偏的唯一保障。
- 契约断言必须做成**本项目要新建的、可发布的包**，供接入方在自己的 CI 里运行。这一步不能省：接入方是独立项目，没有这个包就只能靠人工对齐。既有实现里有同类先例（把契约断言做成可发布包供接入方 CI 使用），做法可照搬，但**这个包要本项目自己建、自己发版**。

### 12.5 客户端渠道的测试边界（需提前说明）

**平台核心与渠道客户端是两套测试体系，不要混在一起。** 平台核心（契约、中转）是纯 Node/TypeScript，适合逐文件执行的轻量入口；渠道客户端（Web 前端、小程序）需要各自的测试方式，小程序渠道还需要真机验证环境。

这个边界必须提前说清楚：不要指望一套入口同时覆盖两端，也不要为了"统一"把渠道测试塞进平台核心的入口。既有的逐文件执行型 Node 测试入口就是一个反例 —— 它无法承载任何 DOM 或真机测试。

### 12.6 纪律

触及契约层、平台服务边界或共享类型的改动，执行这套纪律（**本项目需要自己确立并写进项目规范**）：**逐文件跑相关测试 + 类型检查必须 exit 0**；新增用例需要能被一条对应的代码变异打红（变异验证），锚点恰好命中一次、还原后文件逐字节一致。这套纪律在既有项目中已经被证明能挡住"测试写了但根本没测到"的情况，值得直接采用。

## 13. 里程碑（粗粒度）

任务级拆分见后续实施计划，这里只给粗粒度阶段：

1. **契约层**：核心模型、指令、事件、能力开关、版本协商、内容块复用与限额，配套测试与契约断言包。
2. **中转与渠道层骨架**：连接注册、配对路由、转发、背压、在线状态，以及渠道适配器接口与渠道限制声明机制。
3. **纯 Web 渠道**：Web UI、传输实现、配对界面、断连恢复，以及 `assertion` 模式下的门户 OAuth 断言获取。
4. **第一个接入方接入**：按契约实现常驻接入服务与会话映射 —— **本设计不含其内部改造方案**，仅以"接入方零改动平台"为验收条件。
5. **渠道扩展**：IM 容器 H5 族；微信小程序渠道（其专属风险见 §11）。

阶段 4 可在**阶段 1 完成后**即开始，不必等阶段 2、3 完成 —— 契约一旦冻结，接入方实现即可开始。

## 14. 非目标

- **各接入方侧的具体改造**（会话所有权下沉、常驻服务实现、进程模型等）—— 由接入方自行设计。
- 声明式 UI（客户端界面固定，接入方给数据不给界面）。
- 平台统一账号体系。
- 局域网直连快路径。
- 应用市场与安装期能力同意。
- 移动端的代码高亮、Diff 预览、原文件预览、扩展页面、工作区切换。
- 平台侧"一键撤销已发放的会话密钥"（物理上做不到，见 §8.5）。
- 平台内实现业务并发控制（写指令串行化是接入方责任，见 §8.4）。
- **不把任何渠道特有的东西写进接入契约**（§4.3）。
