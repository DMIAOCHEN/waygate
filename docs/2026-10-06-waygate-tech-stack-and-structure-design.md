## 1. 四个已定决策

这四条是本文其余部分的前提，已确认：

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| 1 | 交付范围 | 设计文档 + 可运行骨架 + `AGENTS.md` | 规矩若不可执行就只是愿望；骨架让门禁从第一天起是活的 |
| 2 | 中转部署形态 | **单实例运行，但连接状态外置的接缝先留好** | 平台设计 §6.7 明确要求"不能默认单实例"被显式确认。默认内存实现，presence／pairing／时钟抽成可替换接口，换 Redis 时不动业务代码 |
| 3 | 纪律强度 | **分层**：契约层最严，其余适中 | 平台设计 §12.6 的措辞本就是限定范围的（"触及契约层、平台服务边界或共享类型的改动"），不做全局最高标准 |
| 4 | 契约单一事实来源 | **TypeScript 类型** | 与平台设计 §12.1／§12.4 一致。接入方是桌面应用，多数能跑 Node，可直接使用契约断言包 |

## 3. 工具链选型

### 3.1 版本策略

新项目取各工具的**最新稳定线**，除非该工具有已知的、与本项目纪律冲突的能力缺口。这与"照抄既有仓库的 pin"是两种策略，理由：既有仓库的 pin 里有一部分是为**它自己的**兼容矩阵（vendor、原生插件、Python 运行时、多 face 构建）服务的，Waygate 没有这些东西。

据此选定的基线（骨架阶段实测确认，见 §11）：

| 工具 | 版本 | 说明 |
|---|---|---|
| `typescript` | `6.0.3`，附 §11 的一条升级验证 | 见 §11 风险一 |
| `vitest` / `@vitest/coverage-v8` | `5.0.3` | 两者主版本必须一致 |
| `oxlint` | `1.87.0` | |
| `oxfmt` | `0.72.0` | |
| `tsdown` | `0.23.0` | 仅应用层使用 |
| `ws` | `8.22.0` | |
| `tsx` | `4.23.15` | |
| `lefthook` | `2.1.17` | |

### 3.2 为什么是这一套

平台设计 §12.5 已经把平台核心定为"纯 Node/TypeScript"，§12.1 把契约层定为"纯 TypeScript"。所以语言没有悬念；真正的选择在于**仓库要背多少机器**。

考虑过并否决的两套替代：

- **零构建最小栈**（`tsc` 直接产出 + `node:test`，不引打包器与 linter）。依赖最少、CI 最快，但代价恰好都落在 §12.6 那条纪律上：`node:test` 没有 per-file 覆盖率门槛；没有 linter 则"防原型查表""`contract` 不得依赖渠道"这类规则只能靠 review 记忆。平台设计把纪律当硬要求，最小栈会把它降级为自觉。
- **平台化重装**（Turbo + changesets + eslint/prettier + playwright + Stryker + 每包多 face tsconfig）。对多团队、多渠道并行的中期形态合理，但它把变更集发布、任务图缓存、变异测试三道工序前置到一个还没有第一行契约代码的仓库上。等真有第二个接入方与第二个渠道时再上，成本更低。

### 3.3 从既有生态抄什么、不抄什么

这一节存在的理由：把既有仓库的工程决策整体搬过来，会把 **90 个包的复杂度**搬进一个 **10 个包的项目**。

**抄 —— 严格性开关**（`tsconfig.base.json`）：

`strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride`、`noFallthroughCasesInSwitch`、`noUnusedLocals`、`noUnusedParameters`、`allowImportingTsExtensions` + `rewriteRelativeImportExtensions`。

其中 `exactOptionalPropertyTypes` 与平台设计 §5.7 的"字段缺失要**省略键**，不要写 `undefined`"是同一件事的两个面 —— 前者是后者的编译器支撑。这不是巧合式的对齐，是刻意选择的：把一条协议层的纪律交给编译器守，比交给 review 可靠。

**不抄 —— `tsconfig.base.json` 里那份几百行的 `paths` 大表**。那是项目引用规模上去之后的产物（既有仓库用它同时充当源码解析门面）。Waygate 用每包 `tsconfig.json` + `tsc -b` 项目引用即可，`paths` 只保留少量确有必要的工作区别名，绝不作为跨包解析的主要机制。

**有意偏离一处 —— `verbatimModuleSyntax: true`**（既有生态设为 `false`）。Waygate 有多个包要发布给外部接入方与浏览器使用，强制 `import type` 让"类型依赖"与"运行时依赖"在编译期就分开：一个只在类型位置用到的 import 不会变成运行时 import，也就不会把一个本可零依赖的包拖进依赖图。既有生态的依赖图里含 `vendor/` 下的第三方代码，需要为互操作留余地；Waygate 没有 `vendor/`，不需要让路。

## 4. 仓库结构

### 4.1 包划分

| 包 | 里程碑 | 发布 | 职责 |
|---|---|---|---|
| `contract` | 1 | ✅ npm | 核心模型、指令、事件、能力开关、版本协商、内容块 schema 与限额。**零运行时依赖** |
| `contract-assert` | 1 | ✅ npm | 契约一致性套件，供接入方在自己的 CI 里运行（平台设计 §12.4） |
| `frame` | 1 | ✅ npm | 信封 `{channel, seq, nonce, ciphertext, tag}`、明文控制帧、编解码、路由字段 |
| `crypto` | 1 | ✅ npm | X25519 ECDH、AES-GCM AEAD、会话密钥生命周期、`seq` 滑窗与防重放 |
| `sdk` | 1 | ✅ npm | 接入方门面：零逻辑，只 re-export `contract` + `frame` + `crypto` |
| `test-support` | 1 | ❌ 私有 | 可注入时钟、内存传输工厂、夹具（平台设计 §12.2 要求可注入） |
| `mock-endpoint` | 1 | ❌ 私有 | 最小接入方实现 —— 平台设计 §12.4 要求的"第二个实现" |
| `relay` | 2 | ❌ 私有 | 注册、配对路由、双向转发、背压丢弃、在线状态、连接元数据审计 |
| `channel` | 2 | ❌ 私有 | 渠道适配器契约、**渠道限制声明**、共享传输实现 |
| `channel-web` | 3 | ❌ 私有 | 纯 Web 渠道适配器：传输 + 身份断言获取 |
| `apps/relay` | 2 | ❌ 私有 | 中转进程装配（bin）+ 内存 store |
| `apps/web` | 3 | ❌ 私有 | Web 渠道前端（React + Vite） |

命名规则：所有包使用 `@waygate/<name>` 作用域。私有包一律声明 `"private": true`；发布包声明 `exports`、`files` 与 `publishConfig`。

里程碑 2／3 的包**现在不建**。理由：建成空包只会得到没有覆盖率的死目录，而且会立刻需要为它们编写门禁豁免 —— 那正好是纪律开始松动的入口。

### 4.2 依赖方向

```
        contract  (零运行时依赖)
         ↑      ↑
      frame     └──── contract-assert
       ↑  ↑              ↑
       │  └── crypto     │
       │        ↑        │
     relay   channel ────┘
       ↑        ↑
  apps/relay  channel-web → apps/web
              mock-endpoint
```

`sdk` 位于 `contract` + `frame` + `crypto` 之上，不被任何内部包依赖（它是给外部接入方的门面，内部包直接依赖具体包，不经门面）。

### 4.3 不变量

这六条是整份设计里最容易被侵蚀的部分。"中转是哑管道"如果只写在文档里，几个月后 `relay` 就会 import 业务模型。因此每条都配了执行方式，`scripts/check-boundaries.ts` 在 CI 与 `pnpm gate` 里跑。

| # | 不变量 | 保护的是什么 | 执行方式 |
|---|---|---|---|
| **R1** | `contract` 运行时依赖数为 0 | 平台设计 §12.1：它必须在浏览器、Node、小程序三种运行时里都能加载 | 门禁：读 `package.json` 的 `dependencies` 必须为空 |
| **R2** | `relay` 的**传递依赖不得包含 `crypto`** | 平台设计 §9.1"平台被攻破也只见密文"—— 中转看不到明文，就不该有解密能力 | 门禁：解析工作区依赖图，禁止该边 |
| **R3** | `relay` **不得依赖 `contract` 的业务模型**，只能用 `frame` 的信封与控制帧 | 平台设计 §4.2"中转不知道自己转发的是会话" | 门禁：同 R2 |
| **R4** | `contract` 不得依赖任何渠道相关的东西 | 平台设计 §4.3 渠道无关性不变量 | 门禁：依赖图 |
| **R5** | 内容块度量与校验只在 `contract` 实现，且**不得使用 `TextEncoder`** | 平台设计 §5.8 的坑（微信小程序运行时没有 `TextEncoder`） | 门禁：lint 规则禁用 `TextEncoder`；渠道包不得导出度量函数 |
| **R6** | 浏览器／DOM 代码只能出现在 `apps/web`；`packages/*` 全部保持 Node 可测 | 平台设计 §12.5"两套测试体系" | 门禁：`packages/*` 的源码不得引用 DOM 全局 |

R2 与 R3 值得单独说一句：它们是**把安全承诺变成编译期事实**的地方。文档承诺"平台只见密文"很容易，但如果 `relay` 能 import `crypto`，那这个承诺就只靠"我们没这么写"维持。禁止这条依赖边之后，它是结构性的。

## 5. 构建与类型策略

### 5.1 只有一条构建路径

`tsc -b` 按项目引用编译全部包，产出 `lib/`（JS + `.d.ts` + sourcemap）。发布包直接以这份产物发布，不额外打包。

**库包不使用 tsdown。** 理由：`tsc` 已经产出合法 ESM 与声明文件；再引一层打包器就会引入"源码平面 vs 产物平面"这条纪律（哪些门禁跑 `src`、哪些跑 `lib`），而这条纪律正是既有仓库需要专门文档去守的东西（其 `AGENTS.md` 里"Source plane vs artifact plane, never mixed"）。Waygate 的包不需要打包就能发布，所以不要这一层。

`tsdown` 只用在真正需要打包的地方：

- `apps/relay` —— 产出一个可执行的 bin；
- `apps/web` —— Vite 负责，不需要 tsdown。

### 5.2 模块解析用 `nodenext`，不用 `bundler`

`module: nodenext` + `moduleResolution: nodenext`。理由：Waygate 的包要发布到 npm、被 Node 直接加载（接入方在自己的服务里 import），也从 `exports` 字段被 Vite 解析。`bundler` 解析是为"源码永远经过打包器"的项目设计的，用它来发布 Node 直接消费的包，等于把风险推给下游。

配合 `allowImportingTsExtensions` + `rewriteRelativeImportExtensions`：源码里本地相对导入写 `.ts`，编译时改写为 `.js`。这与既有生态的写法一致，但它在这里的作用是让**源码路径即发布路径**，不需要另一套 import 映射。

### 5.3 编译器面（compiler face）

只保留两面：

- **平台面**（`tsconfig.json` 根解决方案，覆盖 `packages/*` 与 `apps/relay`）；
- **浏览器面**（`apps/web` 自己的 `tsconfig.web.json`）。

每包一个 `tsconfig.json`，`composite: true`，由根解决方案引用。不预先设计"每包多 face"—— 那是 R6 与 §12.5 之外的需求，现在没有。

## 6. 命令

Waygate 自己的命令集。**不沿用任何既有仓库的脚本名。**

```sh
pnpm install
pnpm build            # tsc -b 全项目 + 应用打包
pnpm typecheck        # tsc -b（增量）；类型门禁
pnpm lint             # oxlint
pnpm format           # oxfmt --write
pnpm format:check     # 只检查，不改写
pnpm test             # 平台核心全套（vitest run）
pnpm test:web         # Web 渠道全套（独立 config）
pnpm test:coverage    # 平台核心全套 + 覆盖率门槛
pnpm test:mutation    # 变异验证
pnpm gate             # 收口：typecheck + lint + format:check + check:boundaries + check:versions + test:coverage
```

`pnpm gate` 是唯一的本地收口命令，CI 跑同一个。开发循环里不跑它 —— 按 §7.2 只跑改动涉及的测试文件（`pnpm test <文件路径>`）。既有生态那份"推送前跑哪些检查"的清单在这里被收敛成一条命令，因为我们没有平台矩阵、原生插件与 Python 运行时需要分情况。

`check:boundaries` 与 `check:versions` 只通过 `pnpm gate` 与 CI 执行，不作为独立日常命令暴露。

## 7. 测试体系与分层纪律

### 7.1 两套互不混合的体系

平台设计 §12.5 点名了一个反例：一个逐文件执行的 Node 测试入口无法承载任何 DOM 或真机测试。Waygate 用结构避免重造同一个坑。

| 体系 | 覆盖 | Config | 环境 |
|---|---|---|---|
| 平台核心 | `packages/*` | `vitest.config.ts` | Node |
| 渠道客户端 | `apps/web` | `vitest.web.config.ts` | jsdom／browser |

**规则**：一个 config 绝不覆盖两者；渠道测试也不许塞进核心入口。这条同时由 R6 在结构上保证（DOM 代码不许出现在 `packages/*`）。

### 7.2 分层要求

"逐文件"在这份文档里有两个不同意思，先分开：

- **每文件有测试** —— 每个源文件都有覆盖它的测试，这是覆盖率门槛的形态（`perFile`）。
- **逐文件执行** —— 改动时按文件跑相关测试，而不是每次跑全量，这是反馈速度的选择。

| 层 | 每文件有测试 | 覆盖率 | 变异验证 | 其他 |
|---|---|---|---|---|
| `contract` `frame` `crypto` | ✅ | **per-file 100%** | ✅ 必须 | 改动须逐文件执行相关测试 + `typecheck` exit 0 |
| `relay` `channel` `mock-endpoint` | ✅ | 跟随契约层，可按文件显式豁免 | 按需 | 时钟／存储／传输**必须外部注入**；测试不得读真实时钟 |
| `contract-assert` | ✅ | 跟随契约层 | — | 断言必须被 `mock-endpoint` 真实跑到 |
| `apps/web` | ✅ | 不参与核心门槛 | — | 独立体系 |

**逐文件执行而不是跑全量**是刻意的：全量套件在本地是慢反馈，而 CI 拥有穷举覆盖。这里的理由比"更快"更硬一档 —— Waygate 的两套体系本就无法用一条命令跑完（§7.1），所以"跑全量"在本地根本不是一个可选项。

覆盖率豁免必须**写在该包的 README 里并说明理由**，不许只写在配置里。理由是配置里的豁免没有解释，下一个人只会看到门槛变低了。

### 7.3 变异验证机制

平台设计 §12.6 要求"新增用例需要能被一条对应的代码变异打红（变异验证），锚点恰好命中一次、还原后文件逐字节一致"。这句话如果没有工具落地，就是一句无法执行的纪律。因此本项目自建一个小工具。

`scripts/mutation-check.ts`，输入 `(文件, 锚点文本, 测试文件)`：

1. 断言锚点在文件里**恰好命中一次** —— 命中 0 次或多次直接判失败；
2. 记录文件字节快照；
3. 用变异体替换锚点，跑该测试文件，**必须变红**；
4. 还原，并断言文件与快照**逐字节一致**。

新增契约层用例时在用例旁声明其变异锚点，`pnpm test:mutation` 统一执行。

**为什么不用 Stryker**：Stryker 是通用变异测试引擎，会为整个包生成成百上千个变异体，跑一次的成本与"确认我新写的这条用例确实测到了东西"这件事不成比例。这里要的不是覆盖率替代品，而是一个**可声明的、随用例一起提交的证据**。

## 8. 版本与发布

- `CONTRACT_VERSION` 是**单一常量**，只存在于 `contract`（平台设计 §5.7）。
- 发布包（`contract`、`frame`、`crypto`、`sdk`、`contract-assert`）使用**同步版本组**：同一个版本号。接入方因此不会组合出无意义的版本矩阵。
- `scripts/check-versions.ts` 强制两件事：发布包版本一致；`CONTRACT_VERSION` 与包版本不矛盾。
- **暂不引入 changesets。** 手维护版本 + 一条门禁，比现在就引入变更集工作流便宜。触发条件：出现第一个外部接入方，且发布频率需要自动化时再评估。

**为什么发布一个 `@waygate/sdk` 门面**：接入方实现契约需要 `contract` + `frame` + `crypto`。没有门面，接入方要装三个包并自己保证版本一致，而"契约版本"与"包版本"会变成两个概念 —— 这与 §5.7"契约版本是单一事实来源"直接冲突。门面让接入方"一个依赖、一个版本谈协商"。

代价是门面会漂移，因此配一条门禁：`sdk` 的公开面必须**等于**被 re-export 包的公开面并集。`sdk` 自身**零逻辑**，只允许 re-export。

## 9. 编码规矩

每条标注执行方式。只写"应当"而没有执行方式的规则等于没有规则。

### 9.1 语言与模块（全层）

| 规矩 | 执行 |
|---|---|
| ESM everywhere；本地相对导入写 `.ts`，由 `rewriteRelativeImportExtensions` 改写为 `.js` | 门禁 |
| `contract` 运行时依赖数为 0 | 门禁（R1） |
| 不把 `undefined` 当 JSON 值：字段缺失**省略键** | 编译期（`exactOptionalPropertyTypes`） |
| 跨边界的不透明 id 用 branded type，不用裸 `string` | 门禁 + 编译期 |
| 查表一律防原型：`Map` / `Object.hasOwn` / `Object.create(null)` | 门禁（lint 禁字面量下标查表）+ 测试 |
| 判别联合 `switch` 到 `assertNever` 收口 | 编译期 |
| 空 `catch` 必须命名错误并说明原因；`try` 只包一条语句 | 评审 |

### 9.2 契约层

| 规矩 | 执行 |
|---|---|
| `CONTRACT_VERSION` 单一事实来源；协商**无交集明确拒绝，有交集取最低版本** | 门禁 + 测试 |
| 未知块类型 → `unknown` 兜底（**强制项，不是可选项**） | 测试 |
| 未知枚举取值 → 归一为默认值，**不判为错误** | 测试 |
| 未知指令 → 明确错误，且**用形状判定而非 `instanceof`** | 测试 |
| 能力到方法的绑定只有一处；客户端遇未知能力只忽略、不失败 | 评审 + 测试 |
| 内容块限额 256 KiB／2000 节点／深度 32；**深度上限是必需的** —— 深层嵌套的合法 JSON 会在远低于字节预算时触发 `RangeError` | 测试 |
| **度量与校验不得使用 `TextEncoder`**；校验只在接入方与平台侧完成，渠道只做渲染降级 | 门禁（R5）+ lint |
| `seq` 是**每个 Endpoint 一条**序列，不是每个会话一条 | 测试 |

### 9.3 中转

| 规矩 | 执行 |
|---|---|
| 中转**只做**平台设计 §6.1 的六件事；超出清单的需求默认属于接入方或渠道层 | 评审 |
| 控制帧只含路由与状态信息，**不得包含业务内容** | 门禁（类型上限制可用字段） |
| 背压丢弃是**正常路径**，不是错误；客户端按 `seq` 重同步 | 测试 |
| 同一 `deviceId` 只允许一个活跃注册；重复注册按幂等重连处理，旧连接被替换 | 测试 |
| 时钟、传输、store 必须可注入 | 门禁（测试中禁止真实时钟）+ 评审 |
| 审计只记连接元数据与交互的发生及结果；**不记业务内容、消息正文、断言内容** | 评审 |

### 9.4 渠道层

| 规矩 | 执行 |
|---|---|
| **渠道无关性不变量**：任何为某个渠道新增的字段、能力或语义都是设计缺陷 | 门禁（mock 渠道零改动测试） |
| 渠道限制只出现在渠道适配器的限制声明里，不渗进契约 | 门禁（R4） |
| 渠道侧不得实现内容块度量与校验 | 门禁（R5） |
| 身份**不裁决**：断言原样转发、不解析、不存储，由接入方自行验签 | 门禁（R2／R3）+ 评审 |
| 降级（不端到端加密）必须显式配置并在渠道限制声明中标注，**不得静默发生** | 测试 |

### 9.5 三条诚实边界不可弱化

平台设计有三处"平台做不到"的显式表述：

- §5.6 平台**无法强制**高危确认，只能见证并审计；
- §8.5 平台**无法撤销**已经发放到客户端的会话密钥；
- §8.4 平台**不做**写指令并发控制，串行化是接入方责任。

**规矩**：任何文档、注释、类型名、错误消息都不得把这三条改写成"平台保证／平台支持／平台会阻止"。评审时把这三条当检查项。

这条规矩保护的是文档最有价值的属性。这三处一旦被后人顺手"优化"掉，安全评估就会得出错误结论 —— 而错误方向恰好是**高估**平台提供的保障。

### 9.6 测试与文档

- 测试描述**行为**，不描述正确性；行为过时就连同测试一起改，并在 PR 里说明为什么。
- 触及契约层／服务边界／共享类型的改动：逐文件跑相关测试 + `typecheck` exit 0；新增用例带变异锚点。
- 契约的对外行为变化**必须同时更新 `contract-assert`**。契约断言是接入方 CI 的唯一对齐手段，它落后于契约就等于契约没变。
- 注释保持局部：不复述代码，不解释远处行为。
- 用词精确："契约"保留给真正的承诺与不变量（前置条件、后置条件、兼容性承诺）；指代响应字段、JSON 校验、模块导出时用准确的词。
- 文件末尾恰好一个换行。

## 10. 骨架范围

骨架交付**里程碑 1 需要的包**，每个包放**真实但最小**的一块，不放占位空文件。目的是让整条工具链（严格 TS → vitest → 覆盖率门槛 → 门禁脚本 → 发布产物）在第一天就是活的。

| 包 | 骨架内容 |
|---|---|
| `contract` | 核心模型类型（含 `Block` 与强制的 `unknown`）、`CONTRACT_VERSION`、branded id、防原型的能力查表 |
| `frame` | `Envelope` 类型、明文控制帧联合类型、编解码往返 |
| `crypto` | X25519 ECDH 派生会话密钥、AES-GCM seal/open、`seq` 滑窗 |
| `contract-assert` | 一条真实断言（未知块类型落到 `unknown`） |
| `sdk` | re-export + 公开面门禁 |
| `test-support` | 固定时钟、内存传输 |
| `mock-endpoint` | 最小实现，使 `contract-assert` 的断言被真实跑到 |

同时落地：根工作区配置、`tsconfig.base.json`、平台核心的 vitest config、oxlint／oxfmt 配置、lefthook，以及三个门禁脚本及各自测试：

| 脚本文件 | pnpm 脚本 | 职责 |
|---|---|---|
| `scripts/check-boundaries.ts` | `check:boundaries` | R1–R6 依赖方向与结构不变量 |
| `scripts/check-versions.ts` | `check:versions` | 同步版本组 + `CONTRACT_VERSION` 一致 |
| `scripts/mutation-check.ts` | `test:mutation` | 变异验证 |

**Web 渠道的第二个 vitest config 不在骨架内** —— `apps/web` 属于里程碑 3，现在建一个没有测试可跑的 config 是死配置。§7.1 的两套体系是目标形态，不是骨架形态。

**骨架不包含**：契约的完整指令集与事件集、版本协商逻辑、内容块限额实现、中转实现、渠道实现。这些属于里程碑 1 的正式工作与里程碑 2。
