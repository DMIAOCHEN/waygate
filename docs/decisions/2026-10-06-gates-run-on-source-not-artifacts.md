# 门禁跑源码，产物只用于发布

日期：2026-10-06

状态：已采纳

## 背景

技术选型设计初稿（[specs/2026-10-06-waygate-tech-stack-and-structure-design.md](../specs/2026-10-06-waygate-tech-stack-and-structure-design.md) §5.1）主张：库包用 `tsc -b` 按项目引用产出 `lib/`，发布包直接以这份产物发布，**不引打包器**。理由写的是"再引一层打包器就会引入源码平面与产物平面的纪律"。

## 问题

那条推理是错的，而且错得不容易发现。

在 TypeScript 工作区里，包与包之间靠 `package.json` 的 `exports` 解析。只要 `exports` 指向编译产物，那么类型解析读到的是依赖包的 `.d.ts`，运行时解析读到的是依赖包的 `.js` —— 于是**测试与覆盖率跑在编译后的 JS 上，而不是你写的代码上**。

后果具体到本项目：契约层那条"逐文件 100% 覆盖率"（平台设计 §12.6）衡量的不再是源码。它会给出一个看起来正确的数字，而那个数字说的不是你以为的那件事 —— 这是最坏的一类错误，因为它不会报错。

关键在于：这条纪律**不是"引不引打包器"能决定的**。它由"包之间如何解析"决定，而任何多包 TypeScript 仓库都必须回答这个问题。初稿把两件不相干的事当成了因果。

## 决策

明确划成两个平面，并且只守一条纪律：

| 平面 | 用途 | 谁在读 |
|---|---|---|
| **源码平面** | 类型检查、测试、覆盖率、门禁脚本 | `pnpm typecheck`、`vitest`、`scripts/*` |
| **发布平面** | 发布产物（ESM + `.d.ts`） | 外部接入方 |

**纪律：门禁不得读产物。** 落实方式：

- 根 `tsconfig.json` 是单一程序，`noEmit: true`，跨包解析靠一行通配 `paths`（`@waygate/*` → `packages/*/src/index.ts`）；
- `vitest.config.ts` 用同一条通配解析到源码；
- 骨架阶段**不产出发布产物** —— 此刻没有消费方，第一个是里程碑 4 的接入方。

## 后果

- `pnpm test` 不需要先构建；覆盖率报告里的行号就是源码行号。
- 骨架里没有 `pnpm build`：一个"能跑但没有产出物的地方"的命令只会误导人。
- `tsdown` 在骨架里未被使用。它属于应用层打包与将来的产物管线，不是库包的必需品。
- 里程碑 4 引入产物管线时，必须补一条门禁：`packages/*/src` 不得 import 任何产物路径。

## 考虑过并否决的备选

- **保持初稿做法**（`exports` 指向 `lib/`，测试跑产物）：覆盖率门槛需要靠 sourcemap 回映到源码。可行，但脆弱 —— 它把一个纯工程约定变成了对 sourcemap 正确性的依赖，而"覆盖率数字是对的"这件事会因此变得难以验证。
- **放弃逐文件 100% 覆盖率门槛**：等于放弃平台设计 §12.6 那条纪律的一半，而那正是本项目最想守住的东西。
